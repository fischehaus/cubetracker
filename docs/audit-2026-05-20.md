## Sub-Agent-Reports

### 1. Hooks

**Was sagt die Doku?**

Hooks sind deterministische Shell-Commands an Lifecycle-Punkten (SessionStart, PreToolUse, PostToolUse, Stop, PermissionRequest, PostToolUseFailure, CwdChanged, FileChanged). Matcher + optionale `if:`-Conditions filtern. JSON-Decisions möglich (deny, additionalContext, permissionDecision). Best-Practices: kurze Timeouts (5-10s), breite Matcher + enge if-Conditions, Exit 0 = OK, Exit 2 = Block.

**Was machen wir aktuell?**

5 aktive Hooks, alle in `.claude/settings.json` registriert, 4 Events genutzt:

| Event | Matcher | Hook | Zweck |
|---|---|---|---|
| SessionStart | startup\|resume | `session-start-context.sh` | Repo-Stand-Dump |
| PreToolUse | Bash | `pre-bash-dev-server.sh` | Block lokale Dev-Server (mit Override-Env-Var) |
| PostToolUse | Bash + `git commit *` | `post-git-commit.sh` | Patch-Notes-Tag-Reminder |
| PostToolUse | Edit\|Write\|MultiEdit | `post-edit-hardcoded-url.sh` | Hardcoded-localhost-Schutz |
| Stop | (alle) | `stop-mini-check.sh` | Session-Ende-Backstop |

**Gap-Analyse:**
- ✅ Gut: zielgerichtet auf echte Projekt-Probleme, breite Matcher mit engen if-Conditions, alle hooks robust (kein jq-Dep)
- ⚠ Ungenutzt: **PermissionRequest** (Auto-Approve sicherer Commands), **PostToolUseFailure** (Diagnose bei git-push-Fail), **CwdChanged** (Repo-Status-Refresh bei /webapp ↔ /backend)
- ⚠ pre-bash-dev-server-Pattern `*uvicorn*` blockt auch `pip install uvicorn` (False Positive bei Dep-Installation)

**Vorschläge:**

| # | Vorschlag | Effort | Risiko | Schwelle |
|---|---|---|---|---|
| H1 | PermissionRequest-Hook für safe commands (git push/status/log, npm test/build) — reduziert Permission-Dialog-Fatigue | 10 Min | Niedrig | ✅ Autopilot |
| H2 | PostToolUseFailure-Hook für git-push-Diagnose (non-fast-forward, SSH-Fehler) | 15 Min | Niedrig | 🤔 Präsentation |
| H3 | README.md-Klarstellung dass `*uvicorn*`-Pattern auch `pip install uvicorn` blockt | 5 Min | 0 | ✅ Autopilot |

Eigener Context, eigener System-Prompt, spezifischer Tool-Zugang, eigene Permissions. ### 3. Settings + Permissions

**Was sagt die Doku?**

4-stufige Settings-Hierarchie: Managed > Local (`.claude/settings.local.json`) > Project (`.claude/settings.json`) > User (`~/.claude/settings.json`). Permission-Regeln: `Tool(specifier)` mit Wildcards (`*`/`**`). Evaluation: **Deny gewinnt immer** → Ask → Allow. Permission-Modes: default/acceptEdits/plan/auto/bypassPermissions. Env-Vars in `settings.json` unter `env`-Key.

**Was machen wir aktuell?**

| Ebene | File | Inhalt |
|---|---|---|
| Project | `.claude/settings.json` | Nur Hook-Config, KEINE Permissions |
| User | `~/.claude/settings.json` | 1 allow: `Bash(curl * https://ntfy.sh/*)` |
| Mode | default | Prompt bei jedem Tool-Call |
| Env-Vars | keine | Standard-Timeouts (120s Bash, 600s API) |

**Bekannte Pain-Points:**
- 2× pre-commit-Tag-Falle (Tag gepusht vor Commit-durch)
- 4× Auto-Mode-Classifier-Blocks: gh api, npm test, ntfy (gefixt), bulk-rm, self-modify
- Plan-Mode nie genutzt obwohl Major-Refactors häufig

**Gap-Analyse:**
- **Allow-List leer im Project** — jeder wiederkehrende Bash-Call triggert Classifier
- **Deny-List komplett fehlt** — kein Safety-Net gegen `rm -rf /*` etc.
- **Plan-Mode-Strategie undokumentiert** — User weiss nicht wann Shift+Tab nutzen
- **Env-Vars ungenutzt** — kein Debug-Logging, kein verlängertes Timeout für Python-Heavy

**Vorschläge:**
